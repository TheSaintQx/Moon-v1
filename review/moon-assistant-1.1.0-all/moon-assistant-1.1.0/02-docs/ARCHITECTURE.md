# Архитектура Moon Assistant 1.1.0

Три независимые функции Yandex Cloud, ноль npm-зависимостей, Node.js 22,
точка входа везде `index.handler`. Общее хранилище — Object Storage
(S3 API, SigV4, path-style).

```
Алиса
  │  POST /  (навык)
  ▼
moon-skill ── index.js (адаптер) ──► moon-skill-core.js
  │                                     │
  │  POST ?ask / ?answer / ?deep        │  GET ?warm / ?poll
  ▼                                     ▼
moon-vision ── index.js (async-адаптер) ──► moon-vision-core.js
                                                │
                                                │ POST action=search|warm|refresh
                                                ▼
                                    moon-knowledge-engine (index.js)
                                                │
                            MediaWiki API ◄─────┴─────► Object Storage
                                                          kb/games/<slug>/
```

## 1. Роли

| Функция | Ответственность | Состояние |
| --- | --- | --- |
| `moon-skill` | диалог с Алисой, распознавание намерения, выбор игры, «подробнее», «ну что там» | `session_state` / `user_state` Алисы |
| `moon-vision` | приём кадров, состояние ответов, два этапа, кэш, `answer_ready`, диагностика | `state.json` в бакете |
| `moon-knowledge-engine` | вики → индекс → выдержки, прогрев, обновление | `kb/games/<slug>/` в бакете |

Каждая функция может быть перезапущена и развёрнута отдельно. Единственная
жёсткая связь — контракты HTTP, описанные ниже.

## 2. Поток вопроса

1. **Навык.** `moon-skill-core.js` разбирает реплику: игра, вопрос, «подробнее»,
   «ну что там», показ объекта. Вопрос уходит в `moon-vision` POST-ом
   с `cid` (детерминированный из `session_id` + `message_id` + текст).
2. **Адаптер навыка.** `moon-skill-index.js` подменяет `globalThis.fetch`
   и превращает POST вопроса в асинхронный вызов (`?integration=async`),
   чтобы не упираться в 4,5-секундный лимит реплики. Если платформа ответила
   не 202, ответ пробрасывается как есть.
3. **Асинхронный адаптер vision.** `moon-vision-index.js` принимает «сырое»
   тело асинхронного вызова, собирает из него обычный HTTP-event и вызывает
   ядро. Дальше опрашивает `?answer=1`, пока запись не станет терминальной.
4. **Ядро vision.** Создаёт запись ответа (`pending`), запускает быстрый этап,
   возвращает короткий ответ, ставит в очередь разбор (`kickDeep`).
5. **База знаний.** `action: 'search'` с `fast: true` — только локальный индекс,
   без вики и без записи в хранилище. `fast: false` — полный поиск с вики.

## 3. Два этапа ответа

Состояния записи в `state.json`:

```
pending ──► processing_fast ──► quick_ready ──► processing_deep ──► deep_ready
   │              │                  │                                  │
   │              └── (пусто) ───────┘                                  │
   └──────────────────────────────────────────────────────────────► failed
                        superseded / cancelled / expired  (в любой момент)
```

- `claimPhase(id, phase)` — CAS по `etag` `state.json`: два параллельных
  вызова не начнут одну стадию дважды. Зависшая заявка старше
  `CLAIM_STALE_S` (150 с) перехватывается.
- `savePhase(id, claimId, phase, out)` — пишет результат только если
  `claimId` совпадает. Быстрый результат лежит в `rec.quick`, разбор —
  в `rec.text`. Один не затирает другой.
- `readyFor(st)` отдаёт стадию (`quick`/`deep`) и `final`; `ack` запоминает
  `ackedStage`, поэтому подтверждение короткого ответа не скрывает разбор.
- `?deep=1` — если разбор готов, отдаёт его; если идёт, отдаёт короткий
  ответ с `deep_pending`; если не начинался, запускает в своей invocation.

## 4. Состояние и гонки

`state.json` — единственный источник истины для vision. Запись идёт только
через `saveState()`: чтение с `etag` → слияние (`mergeState`) → `PUT`
с `If-Match` → при 412 повтор с задержкой. Слияние повыластное:

- ответы — по «версии» записи (`recVer`) и рангу статуса (`RANK`),
  явная отмена побеждает свежий `processing`;
- прогрев — только записи текущей игры (`pickWarm`), иначе результат
  старого прогрева затирал бы статус новой;
- кэш ответов и `users` — объединением по времени.

Раз в час (`BACKUP_MIN_MS`) кладётся копия `backup/state-ГГГГММДДЧЧ.json`.

## 5. База знаний

```
discover  →  register  →  warm  →  search  →  refresh
```

- **discover** — сначала прямые кандидаты `<slug>.fandom.com` и
  `<slug>.wiki.gg` (оба варианта `api.php`), затем веб-поиск.
- **register** — `siteinfo` (язык, название), запись `manifest.json`
  с `gameId`, `language`, `warmStatus: none`.
- **warm** — обзорные статьи по 14 универсальным категориям (персонажи,
  локации, предметы, фракции, квесты, механики, сюжет, концовки…),
  отсортированным по определённому жанру. После каждого шага пишется
  `warm.json` и поля `warm*` в manifest; замок `warmLock` снимается
  в `finally`.
- **search** — план вариантов запроса (original → entity → translation →
  alias → intent), BM25-подобная оценка выдержек с idf, бонусами за точное
  название и раздел, штрафом за служебный текст.
- **refresh** — `list=recentchanges`, сравнение `revid`, перечитывание
  только изменившихся статей.

Индекс игры: `kb/games/<slug>/index.json` (+ `manifest.json`, `warm.json`).
Данные разных игр не пересекаются: ключ включает слаг игры.

## 6. Кадры и оверлей

Приложение отправляет JPEG на `POST /` (тело или base64 в JSON). Кадры
лежат в `frames/`, в состоянии — кольцо последних (`ring`, 15 записей).
По вопросу собирается burst (`FRAMES_TO_MODEL = 6` самых свежих кадров
не старше 120 с) и уходит в модель вместе с вопросом.

Готовый ответ отдаётся в `?poll=1` полем `ready` (`qid`, `text`, `stage`,
`final`). Оверлей показывает карточку и подтверждает показ через `?ack=1`.

## 7. Модель

Yandex AI Studio, `POST https://ai.api.cloud.yandex.net/v1/chat/completions`,
заголовки `Authorization: Api-Key …` и `OpenAI-Project: <folder>`.
Три системных промпта: `SYS` (по кадрам), `SYS_KB` (короткий ответ по
выдержкам), `SYS_KB_DEEP` (разбор). Ответ всегда JSON
`{speech, unk, conf, clarify, marker}`; парсер устойчив к обёрткам и мусору.
`reasoning_effort` отправляется только при заданном `MOON_REASONING`.
Один повтор на 5xx/429/408 и обрыв соединения.

## 8. Ключевые решения и почему так

| Решение | Причина |
| --- | --- |
| Ноль зависимостей | архив грузится в облако как есть, нет шага `npm install` |
| Один `state.json` вместо БД | YDB и PostgreSQL дороже и медленнее для 8 записей; CAS по etag достаточен |
| Свой SigV4 вместо SDK | SDK тянет зависимости и холодный старт |
| Индекс в Object Storage, а не в памяти | тёплый экземпляр живёт минуты, индекс — часы |
| Два этапа вместо длинного ожидания | реплика Алисы 4,5 с, разбор в неё не влезает |
| Разбор отдельной invocation | 105 с лимит функции; короткий ответ не должен ждать |
| Адаптер вместо переписывания ядра | ядро остаётся тестируемым и переносимым |
| Подмена `fetch` в тестах | нет сети, нет секретов, тесты детерминированы |
