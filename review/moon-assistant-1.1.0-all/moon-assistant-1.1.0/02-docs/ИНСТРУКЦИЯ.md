# Лунный Ассистент — что загружать и в каком порядке

Комплект из трёх архивов. Каждый архив — одна функция Yandex Cloud.
Внутри архива точка входа всегда называется `index.js`, как ждёт облако.

Релиз **1.1.0** (9 ноября 2026).

| Архив | Функция в облаке | Версия | Что внутри |
| --- | --- | --- | --- |
| `dist/moon-knowledge-engine-v1.1.0.zip` | `moon-knowledge-engine` | 0.9.0 | `index.js` + `VERSION` |
| `dist/moon-vision-v1.1.0.zip` | `moon-vision` | 4.1.0 | `index.js` + `moon-vision-core.js` + `VERSION` |
| `dist/moon-skill-v1.1.0.zip` | `moon-skill` | 10.1 | `index.js` + `moon-skill-core.js` + `VERSION` |

Контрольные суммы — `dist/SHA256SUMS.txt`. Проверить перед загрузкой:

```bash
cd dist && sha256sum -c SHA256SUMS.txt
```

Архивы уже собраны. Если поменяешь исходники — пересобрать: `./tools/package.sh`.

## Версия 1.1.0 — что в ней

Это версия, которую можно оставить работать без присмотра. Коротко, что
появилось по сравнению с 1.0.0:

| Что | Зачем |
| --- | --- |
| Ответ в два этапа | Короткий ответ сразу, разбор — по слову «подробнее» |
| Рабочий асинхронный путь | Адаптер снова перехватывает вопрос (токен в заголовке) |
| Выдержки из нужного раздела | «Биография» больше не проигрывает хвосту статьи |
| Понятная готовность базы | `warm` в ответе поиска всегда объект |
| Обновление базы по `revid` | Не нужно перечитывать вики целиком |
| `reasoning_effort` по требованию | Модели, которые его не принимают, больше не ломаются |
| Смена игры на стриме | Старые ответы и маркер прошлой игры не всплывают поверх новой |
| Повтор при сбое модели | Один автоматический повтор вместо «не могу подтвердить» |
| Диагностика `?diag=1` | Одна ссылка показывает всё состояние и последние ошибки |
| Часовая копия состояния | Битый `state.json` больше не уносит игру и кэш |
| Токен заголовком | Токен больше не светится в адресе запроса |

Подробности по каждому пункту — в разделе 2, полный разбор дефектов —
в `AUDIT_RU.md`.

## 1. Почему Алиса постоянно просила «ну что там»

Причина не в Алисе и не в таймауте навыка. Алиса даёт навыку около 4,5 секунды
на реплику — это её жёсткое ограничение, обойти его нельзя.

А база знаний на **каждый русский вопрос** делала вот что:

1. переводила запрос через внешний переводчик;
2. шла в живую вики и выкачивала оттуда статьи;
3. читала до 30 страниц из Object Storage;
4. перезаписывала индекс обратно в хранилище.

Только после этого отвечала модель. В облаке это легко превращалось в 10–30 секунд,
а moon-vision ждёт базу максимум 10 секунд. Когда он не успевал, ответ получался
«В базе знаний не нашлось подтверждения. Не вижу свежего экрана» — ровно то,
что было в твоём диалоге.

## 2. Что изменено

### 2.1. `moon-knowledge-engine` 0.6.0

Поиск теперь умеет **быстрый режим** (`fast: true`). В этом режиме функция:

- не ходит в вики;
- не вызывает переводчик (берёт только уже сохранённый перевод);
- читает не 30 страниц, а максимум 10;
- не перезаписывает индекс в хранилище;
- кэширует результат в памяти тёплого экземпляра на 10 минут.

Обычный режим (без `fast`) по-прежнему может дойти до вики — но теперь только
когда локальная выдача слабая. Раньше любой русский вопрос из-за кириллицы
считался «не найденным» и каждый раз тянул вики заново — это и было главной
причиной долгих ответов.

### 2.2. `moon-vision` 2.9.0

- **Два этапа поиска.** Сначала быстрый локальный поиск (лимит 2,6 с). Если он
  дал материалы и модель по ним ответила — ответ готов за пару секунд. Если нет —
  включается полный поиск с вики, как раньше. То есть качество не упало,
  а время в удачном случае сократилось в разы.
- **Кэш ответов.** Повторный вопрос по той же игре отвечается мгновенно, без
  поиска и без модели. Кэш на 30 минут и 24 вопроса, хранится в `state.json`.
- **`answer_ready` для оверлея.** Когда ответ готов, приложение получает его
  в ответе `?config=1` или `?poll=1` в поле `ready` и может показать поверх игры.
  Подтверждение показа — `?ack=1&qid=N`, после него уведомление больше не повторяется.
- **`?progress=1`.** Лёгкий опрос состояния задачи: `pending`, `processing`,
  `done`, `expired`, `none` + сколько секунд прошло. Ничего не запускает,
  поэтому навык может спрашивать его сколько угодно часто.
- **Память контекста.** Короткое уточнение («а кем основан?», «кем?», «а его оружие?»)
  склеивается с прошлым вопросом и для поиска, и для модели. Раньше на «Кем?»
  навык просил повторить вопрос целиком.

### 2.3. `moon-skill` 9.7

- Вопросу отдаётся 3,0 с, остаток реплики — опросу (раньше вопросу 2,2 с).
- Опрос каждые 120 мс вместо 250 мс.
- После опроса делается контрольный `?progress=1` — он забирает ответ, который
  появился между опросами, и показывает честный прогресс: «Ещё собираю ответ,
  прошло 11 секунд».
- Подсказка про оверлей говорится один раз за сессию, а не в каждой реплике.
- Незавершённая задача больше не сбрасывается раньше времени.

### 2.4. Любая игра, тёплая база и вопросы «по смыслу»

Раньше база умела только точное совпадение слов: вопрос «кто главные герои»
не находил статью «Персонажи», потому что слова «главные герои» в ней
могли не встречаться. Теперь:

- **Игра — любая.** Достаточно назвать её Алисе («играю в майнкрафт»,
  «сменить игру» → «Ведьмак 3»). База ищет вики по названию сама, отдельного
  списка поддерживаемых игр нет.
- **База прогревается при выборе игры.** Сразу после «Принято, игра: …»
  функция `warm` тянет из вики обзорные статьи: сама игра, персонажи, локации,
  предметы, механики, сюжет. К первому вопросу статьи уже в локальном индексе,
  поэтому ответ не ждёт вики.
- **База греется ещё с началом стрима.** Приложение сразу после запуска стрима
  шлёт первый кадр и опрашивает `?poll=1` каждые 1,5 секунды — любой из этих
  сигналов запускает прогрев по текущей игре. То есть к первому вопросу база
  обычно уже тёплая, и обновлять APK для этого не нужно.
- **База догревается сама после первого вопроса.** Если прогрев при выборе
  игры не закончился (Алиса не ждёт дольше 1,8 с) или игра пришла другим путём,
  первый же вопрос сам запускает прогрев отдельным вызовом `?warm=1`. Ответ на
  этот вопрос не ждёт загрузки: прогрев идёт параллельно. Триггеров три
  (выбор игры, первый кадр/опрос, первый вопрос), но прогрев всегда один:
  повторные не проходят из-за пауз (2 мин после «занято», 5 мин после ошибки,
  30 мин после неудачи с викой, 6 ч для уже тёплой базы).
- **Двойная загрузка исключена.** В базе есть замок `warm-lock.json`: если
  прогрев уже идёт, второй вернёт `busy` и ничего не скачает. Индекс пишется
  слиянием, поэтому параллельный поиск и прогрев не теряют страницы друг друга.
- **Вопрос получает намерение.** «Кто главные герои», «что это за персонаж»,
  «что за локация», «что лучше из двух» — база понимает тип вопроса
  и подмешивает к выдаче обзорную статью, даже если слова не совпали.
- **Ответ собирается из нескольких статей.** Модель получает 5–7 выдержек
  (раньше 5 и короче) и склеивает из них один ответ: перечисляет героев
  с короткой характеристикой каждого, объясняет локацию, сравнивает два предмета.
- **Сравнение двух объектов.** «Что лучше — дробовик или винтовка» разбирается
  на две сущности, обе ищутся отдельно, и в выдачу попадают выдержки про обе,
  а не только про ту, что чаще совпала по словам.

### 2.6. Смена игры на стриме — старое не мешает новому

Раньше при смене игры могли произойти три неприятности: незавершённый вопрос
по прошлой игре досказывался в новый стрим, маркер ещё 5 секунд подсвечивал
объект с прошлого экрана, а старый прогрев мог перезаписать статус прогрева
новой игры. Теперь:

- при смене игры незавершённые ответы прошлой игры получают статус `cancelled`
  (запись `cancelWhy: game_changed` в `state.json`);
- готовые ответы и маркеры прошлой игры не попадают в `ready` и в `?poll=1`;
- ответ по прошлой игре не отдаётся по `?answer=1` и `?progress=1` — вместо
  него приходит `status: none`;
- результат старого прогрева не может затереть статус новой игры: при слиянии
  состояния побеждает запись той игры, которая в нём сейчас.

Если назвать ту же игру повторно, ничего не отменяется — это важно: повторная
фраза «играю в …» не должна убивать вопрос, который уже считается.

### 2.7. Сбой модели — один повтор

Если модель отвечает 5xx, 429, 408 или обрывает соединение, запрос повторяется
один раз через полсекунды. Это убирает часть ответов «Не удалось проверить
ответ по кадру» на плохой сети. Если и вторая попытка упала, ответ будет честным
«не знаю», а код ошибки запишется в запись ответа (`errorStatus`) — его видно
в `?diag=1`.

### 2.8. Диагностика `?diag=1`

Одна ссылка вместо логов Yandex Cloud. Показывает: версию, сколько живёт
экземпляр, текущую игру и её возраст, возраст последнего кадра и опроса,
состояние прогрева, сколько ответов в каком статусе, размер состояния,
последние 6 ответов с временем и источником (`kb`, `screen`, `cache`),
последнюю ошибку модели и флаги настроек (без самих секретов).

### 2.9. Часовая копия состояния

Раз в час при сохранении состояния в бакет кладётся копия:
`backup/state-ГГГГММДДЧЧ.json`. Если `state.json` когда-нибудь окажется битым,
можно восстановить игру, кэш и последние ответы из ближайшей копии.
Копии не удаляются автоматически — при желании старые можно стирать руками.

### 2.10. Токен заголовком

`moon-vision` теперь принимает токен и в `?token=`, и в заголовке
`X-Moon-Token`. `moon-skill` (10.0) уже перешёл на заголовок: в адресах
запросов токена больше нет, он не попадает в логи прокси и историю браузера.
Старый способ работает, так что уже собранный APK ничего не теряет.

Совместимость: новый навык со старой moon-vision (3.x и раньше) НЕ работает —
старая версия ждёт `?token=`. Поэтому moon-vision загружай первым (он понимает
оба способа), и только потом навык. Обратный порядок тоже безопасен: новый
vision понимает и старый навык. Если совсем нужно откатить навык — вместе
с vision или позже него.

### 2.11. Два этапа ответа

Раньше на вопрос был один проход «поиск + модель»: либо коротко, либо никак.
Теперь у вопроса есть явные состояния:

```
pending → processing_fast → quick_ready → processing_deep → deep_ready
```

- **Короткий ответ** (до 400 знаков) считается только по прогретой базе,
  без вики, и отдаётся сразу в реплику Алисы.
- **Разбор** (до 900 знаков, 3–6 предложений) доготовляется отдельной
  invocation: полный поиск по вики, больше источников, другой системный
  промпт. Короткий ответ он не затирает — они лежат рядом.
- Игрок говорит **«подробнее»** (или «поглубже», «разбор», «детали») —
  навык вызывает `?deep=1&qid=…` и озвучивает разбор. Если разбор ещё
  считается, Алиса честно говорит об этом, а не молчит.
- **«Ну что там»** после короткого ответа тоже забирает разбор.
- Если разбор не удался, короткий ответ остаётся: игрок не теряет то,
  что уже услышал.

Подтверждение показа (`?ack=1`) учитывает стадию: подтвердил короткий
ответ — разбор всё равно появится в оверлее один раз.

Отключить второй этап целиком можно переменной `MOON_DEEP=0` в `moon-vision`:
тогда поведение вернётся к одному ответу, а `?deep=1` будет отдавать тот же
короткий ответ.

## 2.13. Android: токен при сборке

Токена в репозитории приложения нет. `app/build.gradle` объявляет
`buildConfigField "String", "MOON_TOKEN"`; значение берётся из переменной
окружения `MOON_TOKEN` или из свойства Gradle `-PMOON_TOKEN=…`:

```bash
MOON_TOKEN=<токен> ./gradlew assembleNonRootDebug
./gradlew assembleNonRootDebug -PMOON_TOKEN=<токен>
```

Пустое значение сборку не ломает: APK собирается, приложение пишет в лог
`MOON_TOKEN не задан: сетевые вызовы отключены` и не отправляет запросы.

В GitHub Actions токен передаётся секретом репозитория `MOON_TOKEN`
(`env: MOON_TOKEN: ${{ secrets.MOON_TOKEN }}` на уровне job), поэтому его нет
в логах и в кэше. Если секрет не задан, workflow соберёт APK без авторизации —
это техническая сборка, а не рабочий APK.

Токен внутри APK можно извлечь из приложения: это защита от публикации
значения в репозитории, а не полноценное хранение секрета.

## 2.14. Что требуется от владельца перед первым деплоем

1. Перевыпустить `AUTH_TOKEN`/`MOON_TOKEN`, `KB_TOKEN`, статический ключ
   Object Storage и `YC_API_KEY` (раздел 9).
2. Добавить новое значение в GitHub: Settings → Secrets and variables → Actions →
   `MOON_TOKEN`.
3. Загрузить `01-cloud-archives/moon-vision-v1.1.0.zip`; остальные два архива
   не менялись и перезаливать их не нужно. Проверить `?ping`, `?diag`, `?warm`.
4. Собрать APK workflow **Build Debug APK** и установить его.

## 4. Как загрузить

Для каждой функции:

1. Открой консоль → **Cloud Functions** → нужная функция.
2. Кнопка **«Редактировать»** (или ⋯ → «Загрузить код»).
3. Выбери архив из таблицы выше.
4. Проверь, что не изменились:
   - точка входа — `index.handler`;
   - среда — `nodejs22`;
   - таймаут — `moon-skill` 5 с, `moon-vision` 2 минуты, `moon-knowledge-engine` 1 минута;
   - память — 128 МБ / 256 МБ / 512 МБ соответственно;
   - сервисный аккаунт и сеть — как сейчас;
   - **переменные окружения не трогай**, они уже настроены.
5. Сохранить изменения.

Новых обязательных переменных окружения нет ни в одной функции. Ничего
добавлять не надо.

Необязательные переменные, без них всё работает как раньше:

- `SELF_URL` в `moon-vision` — адрес самой функции, который она вызывает
  для фонового прогрева и для запуска разбора. Если не задан, используется
  `https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2`.
- `VISION_URL` в `moon-skill` — адрес moon-vision, который навык вызывает.
  Если не задан, используется тот, что прописан в коде
  (`https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2`).
- `MOON_DEEP=0` в `moon-vision` — выключает второй этап (разбор).
  По умолчанию включён.
- `MOON_REASONING` в `moon-vision` — если задать (`low`, `medium`, `high`),
  параметр `reasoning_effort` уйдёт в модель. По умолчанию не отправляется:
  не все модели Yandex AI его принимают.

Если менял или пересоздавал функции — проверь, что оба адреса указывают на живую
moon-vision. Признак ошибки: в `?diag=1` прогрев подолгу висит в `scheduled`,
а в ответе `warm` нет `ok`. После загрузки архива новые переменные добавлять
не нужно.

## 5. Как проверить после загрузки

Подставь свой токен вместо `<TOKEN>`. Эти команды можно открыть прямо из браузера
(ссылка в адресной строке), если заменить `<TOKEN>`.

Проверка живости:

```
https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2?ping=1&token=<AUTH_TOKEN>
https://functions.yandexcloud.net/d4ekva50kru609d2jg6s?ping=1&token=<KB_TOKEN>
```

Быстрый режим базы знаний проверяется в консоли, вкладка **«Тестирование»**
(из адресной строки не получится — нужен POST с телом):

```json
{"action":"search","game":"Cyberpunk 2077","query":"когда основан найт сити","fast":true}
```

В ответе должно быть `"mode": "local-fast"`. Если у игры ещё нет индекса,
вернётся `not_found` или `indexing` — это не ошибка загрузки.

Прогрев базы по любой игре (тоже POST из вкладки «Тестирование»):

```json
{"action":"warm","game":"Minecraft"}
```

Ответ `"status": "ok"` и `"pages": N` — это количество обзорных статей,
которые легли в индекс. Повторный вызов в течение 12 часов отвечает
`"cached": true` и ничего заново не качает; `"refresh": true` заставит
перечитать статьи (нужно, если игра обновилась).

Вопрос «по смыслу» проверяется так:

```json
{"action":"search","game":"Cyberpunk 2077","query":"кто главные герои игры"}
```

В ответе должно быть `"intent": {"name": "characters"}`, а среди `results` —
статья про персонажей.

Прогрев через moon-vision (то, что делает навык при выборе игры):

```
https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2?warm=1&token=<AUTH_TOKEN>&game=Minecraft
```

Этот запрос занимает до 40 секунд, поэтому его вызывают отдельно,
а не в реплике Алисы. Итог прогрева виден в `?config=1` в поле `warm`:
`status` (`scheduled`, `running`, `ok`, `busy`, `needs_wiki`, `timeout`),
сколько статей загружено (`pages`) и разбивка по разделам (`sections`).

Фоновый прогрев проверяется так:

1. Назови игру и запусти стрим на телефоне, ничего не спрашивая.
2. Открой `?config=1` — в `warm` уже должна быть эта игра (`running` или `ok`).
   Это прогрев от первого кадра или `?poll=1`, без вопроса.
3. Если сразу задать вопрос — он также поставит прогрев, если тот ещё не шёл.

Состояние ответа у moon-vision:

```
https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2?health=1&token=<AUTH_TOKEN>
https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2?progress=1&token=<AUTH_TOKEN>&uid=<UID>
https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2?ready=1&token=<AUTH_TOKEN>
https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2?answer=1&token=<AUTH_TOKEN>&qid=<QID>
https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2?deep=1&token=<AUTH_TOKEN>&qid=<QID>
```

Два этапа проверяются так:

1. Задай вопрос (`?ask=...` или голосом). В ответе `?answer=1` будет
   `"stage": "quick"` и `"deep_pending": true` — это короткий ответ.
2. Повтори тот же запрос с `?deep=1&qid=<QID>`. Должно прийти
   `"stage": "deep"`, `"final": true` и текст длиннее короткого.
3. Повтори `?deep=1` ещё раз — ответ вернётся мгновенно и без нового
   поиска: разбор уже посчитан.
4. В `?diag=1` у записи появится `stage`, а у `answers` — счётчики
   `quick_ready` и `deep_ready`.

Если `deep_pending` всегда `false` — второй этап выключен (`MOON_DEEP=0`)
или не задан `SELF_URL`.

Полная диагностика одной ссылкой:

```
https://functions.yandexcloud.net/d4el6hpg7nh0cui52kd2?diag=1&token=<AUTH_TOKEN>
```

Что смотреть в ответе:

| Поле | Что значит |
| --- | --- |
| `ver` | версия vision. Для релиза 1.1.0 должно быть `4.1.0` |
| `game`, `game_age_s` | какая игра сейчас и сколько часов назад её называли |
| `frame_age_s` | сколько секунд назад был кадр. Больше 120 — экран не идёт |
| `poll_age_s` | сколько секунд назад приложение опрашивало сервер |
| `warm` | статус прогрева базы по текущей игре и число статей |
| `answers` | сколько ответов в каждом статусе (`quick_ready`, `deep_ready`, …) |
| `deep` | включён ли второй этап и какой `reasoning_effort` отправляется |
| `state_bytes` | размер состояния. Больше 300 000 — пора чистить `state.json` |
| `last_model_error` | последняя ошибка модели с кодом и временем |
| `recent` | последние 6 вопросов: текст, игра, статус, стадия, источник, время короткого ответа и разбора в мс |
| `kb`, `model` | настроены ли база и модель (`true`/`false`, без самих ключей) |

Часовая копия состояния лежит в бакете под именем `backup/state-ГГГГММДДЧЧ.json` —
её наличие и есть проверка, что резервное копирование работает.

Как понять, что сработал быстрый поиск: в `state.json` у ответа будет
`"src": "kb"`, а в логах moon-vision (если их получится включить) — строка
вида `kb=ok kbfast=true`. Если там `kbfast=false` — ответ собирался полным
поиском, это нормальный запасной путь.

Проговори Алисе два вопроса подряд один и тот же. Второй должен ответиться
мгновенно — это кэш.

## 6. Что сделать в приложении, чтобы убрать «ну что там» совсем

Серверная часть готова. Готовые правки приложения лежат в папке `android-patch/`:
`FrameCapture.java` и `OverlayView.java` заменяются целиком, подробности —
в `android-patch/README.md`.

Что они делают:

1. Читают новое поле `ready` из того же ответа `?poll=1`, который приложение
   и так опрашивает каждые 1,5 секунды.
2. Показывают `ready.text` карточкой внизу экрана на 12 секунд
   (маркеры и их отрисовка не тронуты).
3. Отправляют `?ack=1&qid=<ready.qid>` — после этого уведомление не повторяется.

APK собирается через GitHub Actions: залить два файла в `moonlight-assistant`,
затем **Actions → Build Assistant APK → Run workflow**.

Пока приложение не обновлено, ничего не ломается: сервер просто складывает
`ready` в ответ, а старое приложение его игнорирует.

## 7. Что честно остаётся

- **Реплика Алисы — 4,5 секунды.** Если ответ не готов за это время, Алиса
  физически не может заговорить сама. Поэтому один «ну что там» на новый
  вопрос останется до тех пор, пока оверлей не покажет ответ сам.
- **Разбор не влезает в реплику.** Второй этап — это ещё один вызов функции
  на каждый вопрос. Он стартует сразу после короткого ответа, но приходит
  только по «подробнее» или через оверлей. Если лимит одновременных вызовов
  в облаке жёсткий, разбор может не запуститься: тогда «подробнее» доделает
  его в своей реплике.
- **Первый вопрос по теме — не мгновенный.** Быстрый путь сокращает время,
  но не отменяет вызов модели. Замеров в реальном облаке я не делал:
  в тестах проверено только то, что быстрый режим не делает внешних запросов.
- **Прогрев не всегда успевает к первому вопросу.** Навык ждёт его не больше
  1,8 секунды (иначе Алиса не успеет ответить), а сам прогрев по большой вики
  может идти до 35 секунд. Тогда первый вопрос соберётся обычным полным
  поиском, а база догреется к следующим.
- **Новая игра — это новая база.** Английское и русское название одной игры
  дадут две разные базы, пока не назовёшь игру так же. Название пиши как
  в вики: «Minecraft», а не «майн крафт».
- **Фоновый прогрев — это отдельный вызов функции.** Он стартует вместе
  со стримом (первый кадр или `?poll=1`) или после первого вопроса и идёт
  параллельно ответу. Если у функции упрётся лимит одновременных вызовов,
  прогрев запустится со следующего сигнала (через 2 мин), а ответ всё равно
  соберётся обычным поиском. После трёх неудачных запусков пауза — 30 минут:
  иначе неверный адрес в `SELF_URL` давал бы вызов каждые две минуты весь стрим.
- **Повтор при сбое модели — один.** Если сеть лежит долго, ответ всё равно
  будет «не знаю»: две попытки по 35 секунд — предел для функции в 2 минуты.
- **После смены игры старый ответ пропадает сознательно.** Если вопрос был
  задан в прошлой игре и ещё считался, его ответ отменяется. Это правильное
  поведение: игрок уже смотрит другой экран.
- **Смысл собирает модель, а не база.** База даёт выдержки, поэтому если вика
  по игре бедная, ответ будет коротким или «не знаю» — это честно, а не поломка.
- **Холодный старт.** Первый вызов после простоя всегда медленнее.
- **Кэш — 30 минут и 24 вопроса.** Старые вытесняются.
- **Логи.** Сейчас у всех функций запись логов выключена, а у moon-vision
  платформа пишет «Логирование недоступно». Если появится возможность
  включить — включи: без логов диагностировать долгие ответы тяжело.

## 8. Откат

В каждой функции есть **«История версий»**. Прежние версии остались со статусом
`Obsolete` — можно открыть нужную и сделать её активной.

Данные в бакете (`state.json`, `kb/`) формат не меняли: новые поля
(`quick`, `fastDone`, `deepKickedAt`, `ackedStage`, `warmStatus`, `warmSections`)
старые версии просто игнорируют. Записи в статусах `quick_ready` и `deep_ready`
старая vision 4.0.0 не узнаёт — такой ответ она покажет как «просроченный».
Поэтому откат vision делай вместе с навыком: навык 10.0 не просит `?deep=1`
и работает с любым статусом.

Порядок отката, если что-то пошло не так:

1. `moon-skill` → предыдущая версия (10.0).
2. `moon-vision` → предыдущая версия (4.0.0).
3. `moon-knowledge-engine` → предыдущая версия (0.8.0), если проблема в базе.

Индекс базы знаний (`kb/games/<slug>/index.json`) читается обеими версиями:
новые поля (`warmStatus`, `warmSections`, `warmGenre`) старый движок
не использует, но и не ломается на них.

## 9. Безопасность — сделать обязательно

На скриншотах настроек в открытом виде видны значения `ACCESS_KEY_ID`,
`SECRET_ACCESS_KEY`, `AUTH_TOKEN`, `MOON_TOKEN`, `KB_TOKEN`, `YC_API_KEY`.
Считай их скомпрометированными.

Порядок:

1. В Object Storage перевыпусти статический ключ доступа.
2. В moon-vision и moon-knowledge-engine обнови `ACCESS_KEY_ID` и `SECRET_ACCESS_KEY`.
3. Придумай новый общий токен: его надо одинаково записать в `AUTH_TOKEN`
   (moon-vision) и `MOON_TOKEN` (moon-skill).
4. Отдельно обнови `KB_TOKEN` в moon-vision и moon-knowledge-engine
   (тоже одинаковое значение в обеих).
5. `YC_API_KEY` перевыпусти в AI Studio и обнови в moon-vision.

После смены токенов старые значения перестанут работать — это нормально.

1. Загрузить три архива в порядке: knowledge-engine → vision → skill.
2. Сказать Алисе «сменить игру» → «Minecraft», дождаться «Принято», затем

4. Проговорить два одинаковых вопроса подряд и убедиться, что второй
   ответился сразу.
5. Перевыпустить ключи из раздела 9.
